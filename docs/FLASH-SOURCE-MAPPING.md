# Flash source mapping reclaim experiment

This experiment remains disabled in production. The [current metadata-fix engine](../benchmarks/results/flash-reclaim-meta66-readiness.json) passes all 43 native tests, separate actual A/B READY-only captures, and reviewed prospective budgets for the fixed screen. The separate fixed-code repack ABBA now passes; its modest gains retain only a conditional prefill lead, with full-task and production qualification pending. The helper releases startup source mapping pages after expert-pointer rebinding, keeping the same files and exact values available for later faults.

The standalone helper compiled, but its first owned-file native fixture refused before any memory advice: `mapped_shard_identity_mismatch`. On a separate owned 4 KiB file, `fstat` reported device `0:55`, while the same inode and full path appeared in `/proc/self/maps` on device `0:32`. This was synthetic file metadata, with no model or user content involved. The failed native receipt is `8e9fd7f6ac8281c02c611eda31d0e8cc4af260ffb80595102de1b88c5f70d5bb`.

Upstream explains this distinction: [Btrfs getattr](https://github.com/torvalds/linux/blob/master/fs/btrfs/inode.c) assigns the subvolume anonymous device, while [proc mapping output](https://github.com/torvalds/linux/blob/master/fs/proc/task_mmu.c) uses the inode superblock device. This source explanation is consistent with the owned-file observation; it is not a binary/source match for the installed kernel.

A separate candidate derives mapping identity only for Btrfs from a temporary no-access shared page mapped from the same held read-only file descriptor. It removes that probe before validating or advising any real source range. Other filesystems keep strict direct device matching. Full path, inode, file identity, read-only shared flags, clean-page checks, inward page bounds and startup quiescence remain required; duplicate derived identities are refused. Ignoring device identity globally is not a valid correction.

The separate V4 fixture passed twice: actual VMA RSS fell from **16,781,312 to 4,096 bytes** for a 16 MiB plus 123-byte file, followed by complete byte equality and 256 observed refaults. Both no-access identity probes were removed. All eight malformed-metadata cases reached their intended failure stage; private/COW/dirty/writable-capable mappings, duplicate identities, unrelated ranges and syscall errors were checked. The native unit peaked at 36,384,768 bytes, with no memory/PID events or swap and all children reaped.

The [earlier full engine qualification](../benchmarks/results/flash-reclaim-native43.json), on plan `508d61b7…`, passed: all 41 original tests plus both new fixtures, all four real-hook architecture gates, zero skips, and all 38 executable hashes checked. The native run took 195.83 seconds with a 972,660,736-byte peak and no memory/PID events or own swap. All callers were rebuilt with that configuration layout. This receipt is historical after the shared experimental workspace advanced to the metadata-fix successor; sealed rollback artifacts were preserved.

The first actual-model READY/close observation completed, but its parent receipt writer failed while trying to create an already-existing capture file. That attempt remains failed; its incomplete capture cannot release inference. A separate write-only correction preserved the original observation and wrote final recovery evidence to a new file for the manual repeat. The allocation-only cleanup result in [the repack report](FLASH-DENSE-REPACK.md) is a different operation after the consumer exits; it does not qualify live mapping reclaim.

The [historical actual-model source-reclaim OFF/ON captures](../benchmarks/results/flash-source-reclaim-ready-pair.json) now pass final snapshot writes, resource checks, EOF/reaping, RAM recovery and lease release. In the ON run, the helper measured source mapping RSS **4,195,115,008 → 0 bytes**, with no surviving no-access probe at READY. Both retained the full packed and ordinary dense destinations. Startup peak stayed about **19.1 GiB**; live source-page reclaim does not remove that earlier peak. No generation occurred.

The unpacked control then stopped before loading weights: its reclaim guard required full shape metadata that the loader only requested for repack. A sealed one-line change now requests that metadata when either feature is enabled. It changes metadata availability; all 17 allocation/graph source hashes remain unchanged. The fresh `66aebe9b…` engine passed all 43 native tests in 199.05 seconds, with a 974,770,176-byte peak, no memory/PID events and all children reaped. The earlier failure and its rollback remain preserved.

Fresh A (repack OFF) and B (repack ON) captures use that same new binary, with source reclaim ON in both. Both passed EOF, process reaping, resource gates, RAM recovery, immutable final snapshots and lease release. Source mapping RSS was zero at READY in both. Their prospective fixed-screen totals are **22,743,365,408 / 22,744,863,520 bytes**, leaving **342,083,808 / 340,585,696 bytes** below the unchanged 21.5 GiB cap. These are reviewed engineering budgets with an explicit 256 MiB contingency, not formal allocator maxima; the actual 2 GiB host reserve and live component/combined ceilings remain mandatory. Both packed and remaining ordinary destinations are charged in full. [Curated prerequisites and budgets](../benchmarks/results/flash-reclaim-meta66-readiness.json).

The 2,520-second launcher request was refused; tightening it to 2,500 seconds satisfied the unchanged deadline gate. The first parity attempt then failed in its harness with a string/integer TypeError and no completed arm. A canonical unsigned memory-counter correction then passed the original-control parity: all 353 tokens and their SHA matched, the independent code oracle passed, and EOF/reaping, RAM/resource gates and lease release passed. The subsequent [complete repack ABBA](../benchmarks/results/flash-dense-repack-screen.json) also passed all four code-oracle, repeatability and lifecycle/resource checks. Prefill was 12.324% shorter and weighted decode 2.301% higher; mean request time was 2.884% shorter with a 355-versus-353-token confound. One paired request speedup missed 3%, so the setting remains a conditional prefill lead with no standalone full task or promotion.
