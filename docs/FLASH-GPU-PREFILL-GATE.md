# Flash Vulkan prefill support gate

The conditional GPU phase remains open. Prefill is a material measured cost, so the old 27B Vulkan result does not settle Flash. This review checks whether the current engine exposes the requested dense/attention-only prefill placement. It makes no driver, speed or correctness claim. [Source-file digests and exact findings](../benchmarks/results/flash-vulkan-prefill-source-gate.json).

The current `PrefillPath` opens a device expert arena whenever streaming is enabled. While device placement is active, its router callback sends expert loads to that arena; this is broader than moving dense/attention work alone. The named `dense-on-device` lever is a different placement mechanism, and the planner currently refuses it. Static GPU-layer placement would also affect decode. None is an interchangeable test of the requested prefill-only configuration.

The pinned Vulkan implementation contains QSA/lightning-indexer paths. Architecture names and earlier desktop pauses do not establish that this backend is unsupported. Before a model test, review an exact placement path that keeps streamed experts on CPU and moves only the intended prefill work, with explicit state/copy lifetimes and admission. A missing implementation must be recorded as that specific gate, not a hardware impossibility claim.

If that support gate passes, run one bounded CPU/Vulkan comparison with exact routing, all 512 experts and native top 10. Measure complete request time, actual device activity, correctness, memory recovery and desktop event-loop latency; reject p95 above 50 ms, a maximum above 250 ms, a pause, an admission failure or a leak. Do not promote on a kernel microbenchmark. No such model comparison has run under this gate.

## Owned kernel qualification: actual failures, bounded correction

[The tiny Vulkan build and native prerequisites](../benchmarks/results/flash-vulkan-precision-prerequisites.json) now run on the Adreno X1-85. Exhaustive CPU half conversion and both explicit/exit GPU cleanup fixtures pass. The first scalar micro trial stops at F32 K512/M64/N64 tiny activations (relative RMSE 0.014921 > 0.005). A scoped default-off switch to the existing FP32 shared-operand shader fixes all six F32 cases; that case falls to 4.0844e-7. The next original gate then rejects F16 tiny at 0.048142 > 0.03. The second trial properly unwinds owners and passes 20 stable recovery samples while remaining failed. Both numerical failures are preserved.

The second scoped correction selects the existing FP32 subgroup shader/accumulator for ordinary F16-weight/F32-activation matrices, preserving stored dtypes and device FP16/QSA support. All 30 numerical cases then pass the original thresholds. The formerly failing F16 case falls to 4.1127e-7 relative RMSE. The first V3 observer still fails because it mistakes repeated shader registrations for unique dispatches; that failed receipt is preserved. A fresh native replay of the unchanged binary passes all 30 cases, complete pre/active/post IPC observation, owner retirement and 20 stable RAM-recovery samples. The corrected observer counts paired registration sweeps and does not claim per-case dispatch proof from those markers.

These results qualify owned kernel correctness and cleanup. They do not establish Flash model throughput, model quality or hardware frame latency. The separate presentation probe compiles and tears down cleanly, but its first native attempt sees zero presented frames while the display is asleep (DPMS off). The display was left asleep. Real presentation feedback and an admitted model comparison remain open.

A separate awake-and-restore retry verifies the same display on, then restores its original off state. It still receives zero presented frames: 1,284 submissions, 1,283 discarded and one unresolved feedback. Teardown and process reaping pass. The global recovery gate also fails on shared/pinned observables. Their last values are retained, but the parent receipt omits its same-moment starting values; ownership and wake causation remain unestablished. This does not diagnose a probe, driver or model leak. Both failures are preserved independently. Current session metadata reports `LockedHint=no`; that does not prove the compositor was unlocked or the surface visible during the attempt. Own-surface output/visibility evidence remains the next diagnostic gate; no frame latency or real-model GPU result is claimed.
